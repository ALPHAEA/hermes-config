# NOTE 笔记重结构化 Skill

在执行 `url-to-obsidian-note` 技能或手动添加笔记到 NOTE 目录后，使用此技能对笔记进行统一的结构化整理。

## 适用场景

- 新增了一篇或多篇笔记到 `NOTE/` 分类目录下
- 笔记中的附件命名不规范或存放在错误路径
- 笔记文件名不是 `【source】title.md` 格式
- 需要补充或维护 frontmatter 中的 `assets` 字段
- 笔记分类需要重新整理或新增目录

## 规则定义

### 1️⃣ 分类目录管理
- 按技术/主题分目录：`Java/`, `Network/`, `SmartHome/`, `IDE/` 等
- 如果新增笔记的主题尚无分类目录，**自动创建**并移入
- 如果某个目录下笔记数量增多（建议3-5篇以上），主题可细分时，**自动拆分二级目录**
  - 例如 `Network/` 下路由器和代理类笔记多时，拆为 `Network/Router/` 和 `Network/Proxy/`
- 空的分类目录可保留备移入，但长期无笔记的目录可标记

### 2️⃣ 文件命名规则
- 格式：`【source】title.md`
- `source` 和 `title` 从 frontmatter 取值
- title 中的特殊字符替换规则：
  - `/`, `\\` → `-`
  - `:` → `：`
  - `?` → `？`
  - `*` → `·`
  - `"` → `'`
  - `<` → `《`, `>` → `》`
  - `|` → `-`

### 3️⃣ Frontmatter 模板
```yaml
---
title: <原标题>
source: <来源，如 知乎/CSDN/微信公众号>
source_url: <原文链接>
author: <作者>
created: <创建日期 YYYY-MM-DD>
tags: [标签1, 标签2, ...]
assets: "[[_assets/<8位MD5哈希>]]"   # 自动添加
---
```

- `assets` 字段指向对应附件目录，在 Obsidian 中可点击跳转
- 无附件的笔记不需要加 `assets` 字段

### 4️⃣ 附件存放规则
- 位置：`_assets/<8位MD5哈希>/`
- 目录名计算：对笔记文件名（不含 `.md`）取 MD5 的前 8 位
  ```python
  hashlib.md5(note_name.encode('utf-8')).hexdigest()[:8]
  ```
- 附件文件名：Unix 时间戳截断到秒 + 原扩展名
  - 用文件修改时间 `os.path.getmtime()` 作为时间戳值
  - 例如：`1781774616.png`, `1783486674.jpg`
- 笔记正文中所有 `![[_assets/...]]` 引用路径必须同步更新
- 旧目录移空后自动删除

### 5️⃣ 跨笔记引用处理
- 笔记改名后，其他笔记中所有 `[[旧文件名]]` 引用必须同步更新为 `[[新文件名]]`
- 执行顺序：**先改名，再处理附件**（哈希基于最终文件名计算）

## 执行顺序

> **⚠️ 关键：哈希基于最终文件名计算！所以必须先改名，再处理附件。**

1. **笔记改名** — 先按 `【source】title.md` 规则重命名，更新跨笔记 `[[wiki]]` 引用
2. **分类整理** — 将笔记归入/创建分类目录（在做附件前完成，确保路径稳定）
3. **计算哈希** — 对最终文件名（不含 `.md`）取 MD5 前 8 位
4. **附件改名+目录改哈希** — 附件改为 Unix 时间戳命名，目录改为 8 位 MD5 哈希名，同步更新正文中所有 `![[_assets/...]]` 引用路径
5. **加 assets 字段** — frontmatter 增加 `assets: "[[_assets/哈希]]"`（无附件的笔记不加此字段）
6. **验证** — 检查所有 wiki 链接和附件引用有效

## 注意事项

- 特殊字符在文件名中的处理要兼容 Linux ext4 文件系统
- 如果有同名文件冲突（同一目录下两个文件被改名成相同时间戳），用 mtime + 序号区分（如 `1781774616_1.png`）。但同一篇笔记的多个附件不应共享同一时间戳 —— 如果发生了，说明文件来自备份还原且所有图片的 mtime 相同，此时应优先用记录中的原始名称，或用序号递增代替时间戳
- `.bak` 备份文件执行完后要清理
- 坚果云同步前确保附件目录和笔记文件名都已更新，以免同步产生冲突
- 跨笔记 wiki 链接检查要遍历 NOTE 下所有 `.md` 文件

## 陷阱经验

### ⚠️ 不要假设附件文件名与正文引用匹配
最核心的教训：**不要假设 `_assets` 目录下的文件名与笔记正文中的 `![[_assets/...]]` 引用匹配**。中间状态可能不一致（如备份还原后附件是时间戳但正文是旧名，或反之）。

**正确做法：**
1. 先扫描 `_assets` 下所有**实际存在的文件**，建立 `rel_path -> full_path` 索引
2. 再扫描笔记正文中的引用，逐一查索引
3. 对每个引用：找到实际文件 → 改名+移动到目标哈希目录 → 更新正文引用
4. 找不到实际文件的引用标记为警告（不做破坏性操作）

### ⚠️ 幂等性
脚本必须能从任何中间状态收敛到最终状态（幂等）：
- 已改名的笔记：跳过
- 已在目标哈希目录的附件：跳过（比较引用路径）
- 已被引用的附件（多篇笔记共享同一文件）：检查目标路径是否已存在，用 `os.path.getsize()` 判断内容是否相同

### ⚠️ 执行顺序：先改名，后处理附件
技能规则规定文件名是 `【source】title.md`，而附件哈希基于文件名计算。所以：
```
改名笔记 → 确定新文件名 → 计算哈希 → 处理附件
```

### ⚠️ 避免文件移动冲突
当多个附件引用指向同一个实际文件时（比如备份还原导致的多引同一文件），只移动一次，后续引用直接更新路径。用字典记录已处理的 `(old_ref -> new_ref)` 映射。

### ⚠️ 验证时要检查引用路径的实际文件存在性
不能用 `len(refs)` 代替文件存在检查 —— 引用数量匹配不等于路径有效。最终验证必须对每个引用执行 `os.path.isfile()` 确认。
